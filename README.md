## 目录结构

```

```

**命名规范**:`T<题号>_<英文短名>.java`,例如 `T001_TwoSum.java`、`T015_ThreeSum.java`。
题号补零到 3 位,方便按文件名排序 —— **这是给自己省事,不是强迫症**。

> ⚠️ **文件名必须和类名完全一致**(Java 对 `public class` 的硬性要求)。
> 从力扣网页复制代码时,类名是 `Solution`,要改成和文件名同名:
> `T027_RemoveElement.java` 里必须是 `public class T027_RemoveElement`。
> 方法参数也一样:力扣会自动生成带下划线的参数名,把它改成正常的命名 ——
> 面试官会点开你的 GitHub 看代码,别让他看到力扣自动生成的痕迹。

## 为什么刷题也要写测试

很多人刷题仓库只有一堆 `Solution.java`,过两个月自己都不敢确认当时写对没有。这里要求每题配测试:

1. **二刷时不用重新想用例** —— 跑一遍就知道实现还对不对
2. **换解法时能立刻验证没改坏** —— 比如把哈希表换成排序+双指针
3. **养成"代码要有验证手段"的习惯** —— 这正是简历项目里最缺的东西,面试官问"你怎么证明它是对的"时你答得出来

每题至少覆盖:**题面示例 + 边界情况 + 一条能打死错误写法的用例**。

## 提交规范

```
feat(T001): 两数之和 —— 哈希表 O(n)
fix(T015):  修正三数之和的去重边界
test(T033): 补充变位词分组的空串用例
notes:      双指针套路总结
```

回填网页提交时,消息后面加 `(网页提交回填,待重写)` —— 这样以后翻历史,
一眼就知道哪几条是"当时过了、但写法还没收敛"的。

**每个 commit 对应一次真实的思考**,不要攒一周再一次性提交 —— 提交历史本身就是"持续在做"的证据,面试官会看。
